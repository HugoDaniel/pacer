# The annotated Pacer score cookbook
This directory teaches the score language as the implementation actually
behaves. Each case is a small score, a machine-checkable `expected.json`, and
a `notes.md` that says what to look at and why. The cases are aimed at two
readers at once: a person learning Pacer, and an LLM that will paste one case
into context and act on it.

Every claim here is checkable by running the case. If a score and its
expectation disagree, the implementation is the oracle; do not hand-edit
`expected.json`.

## What a case contains
| File | Purpose |
| --- | --- |
| `case.json` | teaching metadata, host registries, sample times, load mode |
| `score.sjon` | the score, commented with what it demonstrates |
| `expected.json` | generated by `run.mjs --update`; committed and byte-stable |
| `notes.md` | 4-6 sentences for a human: what happens and what confuses people |

`case.json` carries the `id`, `title`, `aspect` tags, a `teaches` paragraph,
`observe` bullets, `score`, `registries`, `times` and `derives`.
Any case directory is a concrete example.

`registries` is the flat PACT order: entries are grouped by an optional
`:registry` (default 0), registries ascending, arrival order kept inside each.
The flat index is the `target_id` space. `arity` is the target's lane count
(1-4). `derives` currently supports only
`{"kind":"truncate","at":N}`, which slices the case's own packed bytes; no
binary blob is checked in.

Optional `loadMode` is one of `text` (default), `binary`, `both`, `variants` or
`lifecycle`. `variants` adds a `variants` array of `{name, registries}`
alternative joins, each loaded against the same canonical carrier; the
refusal cases use it to show a valid carrier under the wrong join. `lifecycle`
adds a `{badScore, badRegistries}` payload whose `badScore` names an extra
score file (`bad.sjon`) beside `score.sjon`: the runner packs it, offers it to
the already-armed driver, then checks the old frame survives. Other refusal
cases stage their invalid carrier with `derives` or a score that fails to
compile.

## Score grammar as implemented
The schema is the authority (`schema/pacer.sjon`); this is the working
cheat sheet. Forms are S-expressions and keys start with `:`.

### Targets and transport
```sjon
(target :name glow :arity 1 :registry 0)   ; compose-mode, optional
(transport :bpm 120 :meter [4 4] :dur 8b :end loop :emit [beat phase])
(tempo :at 4b :bpm 240)                    ; from beat 4 onward
```

`:bpm` is 1..1000 and may be fractional. `:meter` is `[beats denominator]`;
the denominator is validated but only the beat count is on the wire. `:dur`
takes `b`, `bar` or `s`, and `:end` is `hold` (default) or `loop` (which
requires `:dur`). `:emit` names reserved clock lanes (`beat`, `bar`, `phase`,
`bpm`, `t`) resolved by exact target name; emitted lanes land before track
writes. `(tempo ...)` segments use `b`/`bar` positions, strictly ascending.

### Tracks, keys and easing
```sjon
(track :target radius
  (key :at 0b :value 0.2)
  (key :at 4b :value 0.8 :ease in-out-cubic))

(track :target tint (key :at 0b :value [1 0 0]))
(track :target wave :expr (+ 0.5 (* 0.5 (sin (* (tau) beat)))))
(track :target pulse :pattern (euclid 3 8 0.8))
```

A target's arity is 1..4; a vector key must match it. A track has exactly one
source: `(key ...)` children, `:expr`, or `:pattern`. Before the first key the
track holds its first value; after the last it holds its last. A key's ease
shapes the segment ENDING at that key, and the default is `linear`.

Named eases: `linear`, `hold`, `smoothstep`, `in-quad`, `out-quad`,
`in-out-quad`, `in-cubic`, `out-cubic`, `in-out-cubic`, `in-quart`,
`out-quart`, `in-out-quart`, `in-sine`, `out-sine`, `in-out-sine`, `in-expo`,
`out-expo`, `in-out-expo`.

Combinators:

```sjon
(seq (stage :ease out-cubic :t 0.4 :v 1.15)
     (stage :ease in-out-quad :t 0.35 :v -0.18))
(chain E1 E2)                       ; E2(E1(u))
(steps :n 4 :jump end)              ; or :jump start
(cubic-bezier :p [0.42 0 0.58 1])
(spring :damping 0.3 :periods 3)
```

### Scenes, controls and triggers
```sjon
(scene :name intro :at 0b :dur 6b
  (track :target level (key :at 0b :value 0.1) (key :at 6b :value 0.7))
  (trigger :target pulse :every 1b)) ; schema-listed, not case-verified

(control :id depth :type slider :target gain :min 0 :max 1 :value 0.25)
(control :id pan :type xy :target pan-out :min [-1 -1] :max [1 1]
         :value [0.25 0.5])
(control :id tint :type color :target tint-out :value [0.2 0.4 0.6]) ; schema-listed, not case-verified
```

Scenes are half-open windows `[at, at+dur)`; child positions are
scene-relative, and later scene writes win for in-order consumers. A control
writes its document `:value` every idle frame after all track writes, and binds
under `:id` in every expression; without `:target` it only binds. `:min`/`:max`
are editor rails, never clamps, and only exist for `slider`/`xy`. A trigger
needs exactly one of `:every` or `:at`; it writes `(phase, count, gate,
beats-since)` truncated to the target's arity, and omits the write before its
first event.

### Expression environment and operators
`:expr` and pattern hap expressions use SJON's prefix expression language.
Pacer binds `t`, `tick`, `beat`, `bar`, `phase`, `cycle`, `bpm`, `dur`
(`dur` only when the transport declares it), `scene-beat` and `scene-phase`
inside a scene, and every control id. Arithmetic is variadic and left-folds:
`(+ ...)`, `(- x ...)` (one arg negates), `(* ...)`, `(/ x y ...)`, `(mod x y)`.
Nesting is the precedence. Numbers include `0x` hex integers. Other useful
heads: `(sin x)`, `(cos x)`, `(tau)`, `(pi)`, `(min ...)`, `(max ...)`,
`(clamp x lo hi)`, `(lerp a b t)`, `(length v)`, `(dot a b)`, `(cross a b)`,
`vec2`/`vec3`/`vec4` and `[a b c]` vector literals, comparisons, `and`/`or`,
and `let`. The full closed vocabulary is SJON's core plugin.

Pattern vocabulary: `(pure x)`, `(fast n p)` and `(euclid n k pat)` are
case-verified. Schema-listed, not case-verified: `(silence)`, `(stack ...)`,
`(slow n p)`, `(slowcat ...)`/`(cat ...)` (alias of slowcat), vectors as
fastcat, and bare atoms as pure. One pattern cycle is one bar.
Inside a hap expression `cycle`, `tick` and `seed` are pattern-local (they
shadow the frame env); everything else resolves through the parent scope.

## How expected.json is produced
`run.mjs` builds once, then for each case:

1. runs `pacer pack score.sjon --out <tmp>/score.pacb` with the case's
   `--target NAME:ncomp:registry` flags;
2. loads the text through `Pacer.load` and/or the carrier through
   `PacerRt.load` with the same ordered registries;
3. evaluates each configured time and normalizes the writes;
4. writes `expected.json` only under `--update`, and only when it changed.

A frame's `writes` are `[target, [decimal f32 lanes], ["0x........" bits]]`
sorted by target for stable diffs. The sibling `order` array is the actual
emission order before sorting; it is how controls-write-last and scene
handoffs stay visible.

Floats are pinned twice on purpose. The decimal side is the host-visible
number; the hex side is the raw big-endian f32 bit pattern. A formatting
change, a rounding change, a `-0` or a NaN payload cannot hide behind decimal
printing. `meta.tracks[].keys[].bits` pins the key anchors the same way.

`expected.json` also records `pack` (exit, status, diagnostics) and `load`
(text diagnostics, or runtime `status`/`reason`; `reason` is meaningful only
when `status` is 1). For a refused reload, `live: true` means the old score is
still armed. `retainedReason` appears when a successful load follows a refusal
and the ABI's reason word still holds the old value; it is deliberately not
reported as this load's reason.

## Run it
```sh
# Builds zig-out/bin/pacer, pacer.wasm and pacer-rt.wasm once, then all cases.
node examples/cookbook/run.mjs

node examples/cookbook/run.mjs --case keys-scalar
node examples/cookbook/run.mjs --json
node examples/cookbook/run.mjs --update --case pattern-drop
node examples/cookbook/run.mjs --no-build
```

Exit 0 means every case matched (`N/N cases match`). `--update` rewrites only
failing or new expectations and prints every changed line; a second run
without `--update` must be a byte-for-byte no-op. `--json` prints one JSON
array with one result per case, including the frame count (`frames`) and meta
track count; the frame values themselves stay in `expected.json`.

To add a case: make `cases/<id>/`, write `case.json`, `score.sjon` and
`notes.md`, add the id to the table above, run `--update --case <id>`, read the
generated diff, then run without `--update`. If the implementation and the
intended lesson disagree, change the case (or drop it and say why), never the
pin by hand.

## Reading the wires
Pacer's stable surfaces are blobs and an export set, not a private API:

- `PACT` - targets in. The ordered registries flattened; the flat index is the
  `target_id` space. Loading a PACB against a different join is a semantic
  refusal (reason 9), even when the bytes are canonical.
- `PACD` - diagnostics out on the text path. One record has a pacer/SJON
  source, severity, code, byte span and message.
- `PACM` - metadata out: transport, tracks with key ticks, controls, scenes,
  tempo segments and easing programs. `meta-pacm` reads this back.
- `PACW` - writes out. The 20-byte entries the host consumes each frame.
- `PACB` - the compiled container at rest. `pacer pack` writes it; `PacerRt`
  decodes it. It does not cross the wasm driver boundary.
- `PACR` - pngine's registered payload kind for SJON score text. It is not a
  Pacer blob and is never used to carry PACB bytes.

The boundary is compiler-free on purpose: `Pacer` owns the parser, schema,
compiler and evaluator; `PacerRt` owns only decode + evaluate. The parity case
loads the same score both ways and compares every write, which is the practical
meaning of "the binary runtime has no second interpreter".
